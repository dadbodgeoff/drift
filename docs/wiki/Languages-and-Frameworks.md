# Languages and Frameworks

What Drift reads, and for which languages and frameworks it lists routes, reads authentication and authorization, and tells where an entry point is reachable from. This page is for the engineer deciding whether Drift fits a repository and for the reader who needs to know why a route is missing or reads `unknown`. It uses three words consistently: **listed** (Drift finds the entry point and shows it), **read** (Drift reads what guards it, or what deploys it, and can prove an answer), and **not listed** (Drift does not find it, so it appears in no inventory, recipe or card).

How each statement was checked is marked in the tables: **run** means a small repository using that framework was scanned with `drift 0.1.0-dev` and the entry point appeared in `drift security --json`; **source** means the statement comes from the code or its documentation and was not run for this page.

## Languages

| Language | Files read | Parser |
| --- | --- | --- |
| TypeScript and JavaScript | `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs` | oxc |
| Python | `.py` | ruff's parser |

No other language is read. A Go, Java, Ruby, Rust, C#, PHP or shell source file is not parsed, mined, checked or inventoried; a repository that is mostly another language gets little from Drift.

Left out on purpose, in every language: files over 1 MiB, generated code (a generated-file header, `@generated`, protobuf output, files marked `linguist-generated` in `.gitattributes`), minified code (a line over 5,000 characters), declaration files (`.d.ts`, `.pyi`), files nested or costly enough to endanger the parser, and files that are not UTF-8. Directories never entered: `node_modules`, `.git`, `.next`, `.turbo`, `.vercel`, `.drift`, `dist`, `build`, `out`, `coverage`, `vendor`, `storybook-static`, and for Python also `__pycache__`, virtual environments (`.venv`, `venv`, any directory holding `pyvenv.cfg` or `conda-meta/`), `site-packages`, `.tox`, `.nox`, `.eggs`, `*.egg-info` and tool caches. Python schema migrations (numbered Django migrations, Alembic and Flask-Migrate revisions) are skipped. `.gitignore` and `.ignore` files in each directory are respected; a global git ignore and `.git/info/exclude` are not, so results do not depend on the machine. `drift scan --json` lists skipped files and the reason.

Conventions are mined from any parsed code, whatever the framework. What follows concerns the parts of Drift that need to know where a request enters: the security inventory, the practice map, a file's card and the hooks' recipes.

Entry points carry a kind: `http`, `page`, `server_action`, `rpc`, `graphql`, `job`, `cron`, `consumer`, `cli`, `agent_graph`. A `consumer` takes what a broker hands it, so it is listed apart and counted in no authentication or authorization concern; a `cli` entry point is local and never counted as having no guard.

A route registered in a way Drift cannot read (a loop it cannot unroll, `getattr(views, name)`, a router built from a non-literal) is not listed, or is listed with its path shown as `?`; the card and the inventory say so under what is not known. In TypeScript and JavaScript, a registration written as a route is (`x.get("/path", (req, res) => ...)`) that no listing accounts for is counted and named by `drift security` (`N registration(s) written as a route is are NOT LISTED`, `unlisted` in `--json`), so a route Drift missed is said, not silent. Python does the same for every framework it reads, one entry per registration with why (`reason`: a view not found or computed, a package's view, an include or mount Drift cannot follow, a URLconf nothing reaches, a Starlette table not read); see [Security Inventory](Security-Inventory). What is listed with a `?` is not said twice.

**How a route registered inside a function is guarded.** What the function registers before the route, in the order written, runs before it, as in a module. What is registered on the same router anywhere else (by the module, by another function) may run before it or not, depending on when the function is called: where there is any, the route's guard is unknown (`opaque`), never "no guard found". A route the module registers itself, on a router a function or a condition registers a middleware on, is unknown the same way. A middleware of a package that never authenticates (a logger, a body parser) leaves nothing unknown.

## Frameworks not listed

These were tried on a small repository and their routes did not appear (**run**): Hapi, Restify, Astro, Tornado, aiohttp and Bottle. (Quart, django-ninja, Litestar and Sanic are listed since the last measured build, from small test repositories only; see the table above. Koa, Remix and React Router, SvelteKit and Nuxt are listed since the last measured build; see the table above. Their routes are listed with their guard unknown unless one is found in the handler's own body, because what runs before them is not read.) The same holds, unverified, for any framework not in the table above. For such a repository:

- `drift security` lists none of its routes, `drift practices` has no recipe for them, and a card says it knows no entry point for the file.
- Convention mining, `drift check`, the review flow and the hooks' rule priming still work on the code as code.
- The statement "no guard" or "none" cannot be made about a route Drift does not list; absence from the inventory is not a finding.

Treat a missing route as a gap in what Drift read, and check it yourself.

## Authentication and authorization: what is read

What stands where a guard goes (a middleware argument, a hook, a wrapper, a decorator, a dependency, a permission class, a tRPC step) is read by one rule per language. The answer is one of three things, and **unknown is the default**.

| Where the guard comes from | Read as |
| --- | --- |
| A function or class of the repository whose body is read to refuse every request without identity | a guard |
| A function of the repository whose body is read to the end and never refuses | nothing |
| A function of the repository that refuses some requests only, or is not read to the end, or hands back something Drift cannot read | unknown |
| A library's guard in a call shape on a closed list | a guard; with an option that lets a request without identity through (`credentialsRequired: false`, `optional=True`, `auto_error=False`), nothing |
| A library value on the list of things that never authenticate (`cors`, `helmet`, body parsers and similar) | nothing |
| A package on neither list, a value of unknown origin (a parameter, a computed access, a conditional), a composition that is not read | unknown, never "no guard" |

**A guard given through an instance (TypeScript and JavaScript).** `const session = new Session(db)`, then `app.get("/x", session.required, handler)`: what stands there is read as the method of the class the instance is made from, by that method's own body. This holds for an instance the module builds in a `const` from a class of the repository and nothing else, and for a `const` that holds a member of one (`const need = session.required`); for an instance a function builds in a `const` at the top of its body, where that function registers the routes; and for a function a constructor function assigns on `this` at the top of its body (`function Session(db) { this.required = (req, res, next) => { ... } }`), through `require` as through an import. A method that refuses no one leaves the route with no guard. One that refuses some requests only, an instance held in a `let`, one chosen by a condition, and a member a constructor assigns twice stay unknown.

**What "read to the end" takes (TypeScript and JavaScript).** A body is read to the end where everything it calls is the runtime's, a package's that does not authenticate, or a function of the repository read the same way, and it does not hand the request, the response or the continuation to what is not read. Three things a body does are read for what they are: a method of a plain value its module holds (`seen.forEach(...)` of `const seen = []`, `cache.get(token)` of `const cache = { get(k) { ... } }`, a method of the same object called through `this`) is a built-in's method or a function written in that value; a method of a local that holds a value of a parameter (`const path = req.url.split("?")[0]`, then `path.endsWith(x)`), and what a callback over such data is called with, are data of the request and not the request; and a call that verifies a token in a branch taken only where the request carries one (`const token = req.cookies.token; if (token && ...) { jwt.verify(token, key) }`) refuses no request for carrying none, so the middleware is not the sign-in guard. A verification every request reaches, one under any other test, a `throw`, a 401 or 403, and a request handed to a method of a value that may answer it keep the middleware unknown.

More of what a body does is read for what it is, each with the look-alike that stays unknown:

| What the body does | Read as | Stays unknown |
| --- | --- | --- |
| A method of the runtime's global object under a name of the module's own (`const shared = global as typeof globalThis & { io: Server }`, then `shared.io.emit(...)`) | the runtime's | a binding that holds anything else |
| A method of plain data: a local read off it, the items of a loop over it (`for (const mark of seen)`), what a function that hands back only plain data gave (`previous().at.getTime()`) | a built-in's method | a value a call the facts do not read made |
| A method a class of the repository inherits from a package's class (`class Visit extends Model`, then `visit.save()`), with any of a promise's own methods on the call | the package's method | a method the class, or a class of the repository above it, declares |
| A promise's own method on the call of an asynchronous function (`report(path).catch(() => {})`) | the function is read; what it rejects with goes to the handler written there | a function that answers 401 or 403 itself |
| An asynchronous function of the repository nothing waits for (`void tally(path);`, `tally(path);`) | what it throws rejects a promise nobody holds | the same function under `await`, returned, or kept in a local |
| A `throw` in a function handed to `then`, `catch` or `finally` on a chain that is a statement nothing waits for | rejects the promise the method made | the same chain under `await` |
| A verifying call made only where what another function handed back is there (`const token = tokenOf(req); if (token) { jwt.verify(token, key) }`), where every value that function returns is a credential the request carries, a part of one, or what a method of one made | refuses no request for carrying none | a function that can hand back anything else (`req.query.label ?? "none"`) |
| A method of a parameter given a parameter typed as plain data (`found.path.match(wanted)` with `wanted: string \| RegExp`) | a method of data | given a parameter with no type or any other type: it may be the request |

**What a route is given last (Express, Fastify, Hono, Koa).** The last function a route is given is a function like those before it. A call handed no function stands where a guard may: `app.get("/users", requireUser())` is guarded where `requireUser()` builds a guard, by the same reading a middleware written before a handler gets. Where the call's callee hands back the one function written in it and that function serves the request (`app.get("/me", currentUser())`), its body is the handler's body: a check in it that answers 401 is the route's own check. A function written in place in what a wrapper was handed (`wrap(async (req, res) => { ... })`) is the handler's body too. One that calls its continuation with nothing (`next()`, not `next(error)`) is a middleware wherever it stands, and is read as one: `app.post("/cards", stamp())`, where `stamp()` answers 401 when reading the session throws, may be the guard of the routes registered after it, so the route is unknown and never `none`.

**One list of library guards.** An export is a library's own guard where the guard lists read the shape of its call, under each name the library exports it by: express-jwt's `expressjwt` and, before version 7, the module itself (`import expressJwt from "express-jwt"`).

The closed lists are `crates/drift-core/src/guard_lists.rs` (TypeScript and JavaScript; it includes, for example, passport, express-jwt, Hono's `jwt`, `bearerAuth` and `basicAuth`, `@nestjs/passport`, `@fastify/auth`, next-auth, Clerk and Supabase helpers) and `crates/drift-mine/src/py_guards.rs` (Python; for example Django's `login_required` and `permission_required`, `flask_login`, `flask_jwt_extended`, FastAPI's `HTTPBearer`, Starlette's `requires`). A guard is read from its body, never from its name.

`known` for authorization needs a check that was read where it is and is proven to run, and to decide, on every request to the route, comparing the caller with the resource or the request. A check that was found and is not proven (under a branch, after a return, in a callback, not awaited, after a write) leaves the unit `unknown` with the reason `check_not_proven`, worded as an unknown. A value of the caller handed to a query or compared is also `unknown`, never `none`. For TypeScript, a query filtered by the session's own value is `unknown`, because where a filter's value comes from is not recorded for TypeScript.

The consequence for how to read an answer: `known` is proven; `none` and `internal` mean **nothing found in what Drift read**, and on code Drift was not tuned on a share of them are wrong. See [Accuracy and Limits](Accuracy-and-Limits).

`identified` is the state of authentication that identifies the caller and turns no one away; it is counted apart from `known`. `none` and `internal` carry what Drift read and what it saw and did not read (`basis`, `exposure_basis`); see [How Drift Works](How-Drift-Works#what-a-none-or-internal-carries).

Readings worth knowing, one sentence each:

- **Python class-based views** are read per handler method (`Class.get`, `Class.post`), through the method that runs, in C3 order, with what the framework runs for every request before the handler; a check in one method is never another's. Where the order cannot be worked out, the unit is unknown.
- **A check, a guard or a webhook verifier counts only when it runs for every request before any work** (any call other than reading the request) and with no earlier return that serves; a verifier may be in a function the handler calls. Otherwise the unit is unknown, never known (Python; TypeScript reads "for some requests only" the same way).
- **TypeScript: a branch on a value of the caller whose exit Drift does not read** (a refusal builder's response returned through a local, a ternary or an `else`; a refusal after a branch that serves; a status written as a name) is unknown, never "identified" or "no guard found". `unauthorized()` / `forbidden()` refuse by what they resolve to (Next.js and the listed HTTP-error packages), not by name. Stripe `constructEventAsync` counts only when awaited or returned; a verifier given a secret written in the code is `signature_not_proven`. A Next.js configuration spread in, re-exported or merged into (`...base`, `export { default } from`, `Object.assign`) is not read. A sign-in check that refuses where the secret matches, or one read through a local assigned more than once, is unknown. An order comparison of a member of the caller with a literal (`level >= 3`) is a role gate, not "no scope"; only an expiry or a count compared with a clock or a bound is. A 401 under a condition that reads nothing of the request or the caller (a maintenance flag, a size limit) is no sign-in check.
- **A tenant filter's answer does not depend on the column's name** (Python and TypeScript): a key on no list reads unknown, never `none`.
- **TypeScript: a response built as a value** refuses only where it is returned; a refusal builder checks no one.
- **Nest providers, ORM configuration and Next.js configuration** Drift cannot follow make the routes they may reach unknown.
- **A Next.js page under a layout that turns away whoever is not signed in** reads *guard unknown* (`layout_may_redirect`), naming the layout's file and line: a layout and its page render in parallel and a layout is not re-run on client navigation, so Drift does not count it as guarding the page. Check in the page or its data layer. Route handlers and server actions are not covered by layouts.
- **A webhook that verifies the sender's signature** (svix or standard-webhooks `Webhook.verify`, Stripe `construct_event` / `webhooks.constructEvent`, Slack `SignatureVerifier.is_valid_request`), for every request, with a failure that leaves the handler, is service authentication, listed by `drift security` under *Entry points that verify a webhook signature (no sign-in by design)*. A verification that is swallowed, only logged, made for some requests only, or whose result is ignored reads `unknown` (`signature_not_proven`), never known. Not yet recognised: TypeScript standard-webhooks and Slack verifiers. A constant-time compare (`timingSafeEqual`, `hmac.compare_digest`) is a check only where its answer decides a refusal.
- **TypeScript: a refusal through the framework's continuation.** On the branch for a caller who is not signed in, `return next(err)`, or `next(new Error(...))` followed by a `return` in the same block, is a refusal: the framework answers for the error. The continuation is the last parameter of an Express or Koa signature, by position. `next("route")` refuses no one. A trailing `next(err)` with no `return` is not read as a refusal.
- **TypeScript: an error class that refuses by its own status.** A class of the repository whose constructor sets a single 401 or 403 (`super(403, m)`, `this.statusCode = 401`, a `status = 403` field) is a refusal of that status where it is thrown. A class whose status is set by a base in another module carries none, and is read as before.
- **TypeScript: functions held by an object or a constructor function.** `export const guards = { async authenticate(req, reply) { ... } }`, and `function Session(db) { this.required = (req, res, next) => { ... } }` used as `new Session(db)`, give each function a symbol of its own (`guards.authenticate`). Where one is given as a guard, that function is read, not the object. A key assigned more than once is not read.
- **TypeScript: handlers behind wrapper calls and factories.** `asyncHandler(ctrl.list)`, `ctrl.list.bind(ctrl)` and `asyncHandler(searchProducts())` are read through to the handler. `app.use("/ftp/:file", servePublicFiles())`, a handler a factory of the repository builds for a path with a parameter, is listed as an `ALL` route. A factory of a package or a global builds nothing Drift can read and is not listed.
- **TypeScript: validation through a helper.** A package's call handed what the request sent and a schema (`parseWithZod(formData, { schema })`) is validation with that schema's library, whatever the call is named. A function of the repository handed both, or a callee that does not resolve, is not followed: `unknown`.
- **TypeScript: a generated database client.** The client a Prisma schema of the repository generates (an import that resolves to no file) is read as Prisma's, including through a module's own binding.
- **TypeScript: test requests and status checks.** Cypress `cy.visit` and `cy.request` are test requests, and `assert.equal(res.status, 401)` of `node:assert`, `assert` or `chai`'s `assert` is a status check, in either order. A negated assertion checks no status.
- **TypeScript: which argument reaches a risky operation.** Drift records which parameter of a function the operation's operand is read off, and which argument each call hands on, so `fed` in `drift security` follows the argument by its position, not only the function. A value handed on after a spread is not followed by position.
- **Python: typed parameters and return annotations.** A handler whose every input arrives through a parameter the framework parses by its declared type (a FastAPI parameter annotated `uuid.UUID`, `EmailStr` or a model; a Django or Flask converter such as `<uuid:pk>`), and whose body reads no other input, validates its input: a value the type does not take is answered with an error. A FastAPI handler's return annotation is read as its response model; `response_model=None` makes none.
- **Python: Django and DRF.** `admin.site.urls` is one entry point guarded by `AdminSite.admin_view` (active staff users); `admin_view` in decorator position is read and is `unknown`. `permission_classes` on a base that is not DRF's is not credited. A class that serves routes (`AnalyticsEndpoint.as_view()` in `urlpatterns`) is a handler, never a database client. A `raise` in an `except` turns away only the requests whose `try` failed, so the code after it is no longer read as skipped. Checks two helper methods deep in a permission class are not read.
- **Unscoped keys and learned scope keys.** An entry point that signs the caller in and takes a tenant or owner key from the request, which nothing it runs, read to the end, checks or filters a query by, is the finding `unscoped_key` (`unscoped` on its unit in `drift practices --json --units`). Which keys tie rows to a caller is learned from the repository's own code: a key counts when at least 3 bodies of production code filter by it with a value of the caller, over at least 3 different query targets. The lists of names are only a fallback.
- **Lowering versions in this build:** Python 75, TypeScript 87 (see [Versioning and Upgrades](Versioning-and-Upgrades)).

### Known gaps stated in the project's documents

- Django: views registered by a custom decorator that stores them in a registry are not listed; settings are read as literals only (`DJANGO_SETTINGS_MODULE` from `manage.py`, `wsgi.py` or `asgi.py`, not from the environment); a `ModelAdmin`'s permissions are not modelled.
- DRF: a `get_permissions()` override is read handler by handler only where its body does nothing but test the request's method or the view's action and return lists of classes ([Practices Map](Practices-Map)); any other body leaves the handler's permissions unknown. `get_authenticators()` overrides are not read (the defaults are assumed), nor are `permission_classes` set by third-party base classes.
- Django: an access mixin (`LoginRequiredMixin`, `PermissionRequiredMixin`, `UserPassesTestMixin`, or a mixin of the repository whose `dispatch` refuses) is a guard where it comes before the view class in the order Python looks methods up (`class V(LoginRequiredMixin, ListView)`); after it (`class V(ListView, LoginRequiredMixin)`) it never runs and is no guard, and where what comes before it is not read, the guard is unknown ([Security Inventory](Security-Inventory)).
- Flask: hooks registered through extensions (`init_app`) of installed packages are not seen. A blueprint built in a factory that takes its guard as a parameter is not yet read.
- FastAPI: ASGI middleware is not a guard; a prefix that is not a literal shows as `?`. A router mounted under several parents gets the routes and dependencies of one parent only.
- NestJS: a guard whose body reads the request through a local is unknown; an `APP_GUARD` provided by a factory or a condition is not read.
- Python: dynamic imports (`importlib.import_module`) are not imports.

The Python adapter record (`docs/v2/PYTHON.md`) is dated 2026-11-05 and is kept as a historical record; the lines above are the ones the project's accuracy notes restate for the current build.

## Errors, validation and the rest of the practice map

The practice map covers nine concerns: `authn`, `authz`, `errors`, `logging`, `api`, `validation`, `config`, `data_access` and `testing`. `authn`, `authz`, `validation`, `errors` and `api` make the recipe agents are given; `logging`, `config`, `data_access` and `testing` are a preview, shown in a recipe only where at least 60% of the package does the same. Both languages feed the same map, and a unit Drift cannot classify is `unknown` with a reason (`unparsed`, `opaque_wrapper`, `unresolved`, `no_symbol`, `dynamic`, `body_unreadable`, `not_followed`, `route_not_matched`, `unclassified`, `check_not_proven`), counted against coverage and never hidden. A table of support per language and concern is not published: run `drift practices --package <dir>` and read the `unknown` reasons for your own code. `drift practices --hints` lists the `.drift/config.yaml` lines that would classify what Drift cannot tell alone. See [Practices Map](Practices-Map).

## Exposure: what Drift reads to say where an entry point is reachable from

| Description | Read? |
| --- | --- |
| Docker Compose files (`compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`, and any YAML file with a `services` mapping, to six levels deep), with their override files | Read: a service that publishes `ports` is `public`, one that does not is `internal`, unless a gateway in the file fronts it. |
| nginx configuration, Traefik labels, Caddyfiles, read from a compose gateway | Read, route by route: a service a location proxies to is public, one nothing proxies to is internal when everything was read and `unknown` otherwise. HAProxy and Envoy images are recognised as gateways, but their configuration is not read. |
| Terraform | Read only where a person tied the code to a target group with `security.terraform`: then its load-balancer listener rules are read for that code. Otherwise recognised, not read. |
| Kubernetes, Helm and Helmfile, Kustomize, CloudFormation, Serverless, Pulumi, Nomad, Fly.io, Render, Netlify, Vercel, Procfile, App Engine, Terragrunt | Recognised and **not read**. While one is in the repository and is not left out with `security.not_deployed`, nothing is said to be `internal`. |
| `security.internal`, `security.public` in `.drift/config.yaml` | Read: a person's statement, which wins over compose. |

`drift security --json` lists the recognised-but-unread descriptions under `boundaries.unread`. See [Security Inventory](Security-Inventory) and [Configuration Reference](Configuration-Reference).
