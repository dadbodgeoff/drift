> kept as written, apart from this note. It is not current documentation:
> behaviour, output and figures may have changed since. The [README](../../README.md)
> describes the current product, and its
> [Limits of the beta](../../README.md#limits-of-the-beta) gives the current
> precision figures and their sources in `eval/study/runs/`. Precision figures
> here are development-set figures under the tier and rubric of their date, and

> call wrappers and layering only, Python advises only, and the default tier
> ships as advise until it measures ≥ 95% on a held-out set.

Nov 5, 2026

**Drift now lowers Python into the same language-neutral facts it produces for
TypeScript, so mining, `check`, the hooks, MCP and `drift security` work on Python
and mixed repos unchanged.** On 8 pinned public repos (165,635 import rows) Drift
implements its documented root policy and CPython's finder order: CPython's
`PathFinder` and an `ast`-based origin follower agree with it on every judged row
(0 disagreements; 2 gaps, both imports of names that do not exist). The import-root
policy itself is shared with the oracle, not independently checked. Recall of
module-level names and exports against CPython's `ast` is 100%, and Drift finds
FastAPI, Flask, flask-restx, Django, DRF and Celery entry points. The largest repo
(saleor, 2,914 Python files) scans in about 0.8 s with a 142 MB peak.

The work lives in `crates/drift-py`. Changes elsewhere are small and listed at the end.

## Parser: Astral's ruff parser

| Criterion | ruff (`ruff_python_parser` 0.0.20) | tree-sitter-python 0.25 | rustpython-parser 0.4 |
| --- | --- | --- | --- |
| Modern syntax | 3.14: PEP 695 generics, `type`, `match`, PEP 758 `except A, B:`, t-strings | Grammar lags CPython releases | Stalled before 3.12; the project moved to a ruff fork |
| Error recovery | Full AST plus error list | Error nodes in a CST | First error aborts |
| AST quality | Typed AST, visitor, tokens with comments | Untyped CST: every node kind by string | Typed AST |
| Speed (spike) | saleor, 28 MB of Python, in 0.27 s on one thread | Similar order, plus CST to AST work | Slower; no recovery |
| Maintenance | Astral, weekly releases, used by ruff and ty | Community grammar | Unmaintained upstream |
| Build and licence | Pure Rust, MIT, **on crates.io** (no git source) | C compiler needed | Pure Rust, MIT |

Decision: ruff, pinned exactly (`=0.0.20`), because the 0.0.x API may change in
any release; bump it deliberately with the conformance snapshots. The crates need
Rust 1.97, which is the pinned toolchain; the workspace `rust-version` is 1.97.
No git source was needed. `cargo deny` required one licence exception:
`ruff_unicode_names2` (the `\N{NAME}` table) carries Unicode-DFS-2016, the
predecessor of the Unicode-3.0 licence already allowed; it is allowed for that
crate only.

Spike results on the 8 dev repos: 0 files with parse errors except 10 Jinja
templates with a `.py` extension in polar (`sdk/generator/python/template/**`).
ruff accepts 3.14 syntax that CPython 3.13 rejects (full-stack-fastapi-template
uses `except InvalidTokenError, ValidationError:`), so the oracle runs on CPython 3.14.

## Pipeline

Same shape as `drift-ts`: ingest, lower each file (cached by content hash under
parser tag `py-l1-<version>`), link (resolve, follow re-exports, confirm adapter
registrations across files), repo pass (test pairing, models). `drift scan` runs
both parsers and merges their `RepoFacts`, then normalises, so output is
byte-identical across thread counts and checkout paths (tested per fixture and for
a mixed repo).

### Ingest

`drift_core::ingest::ingest_lang(root, Lang::Python)` defines which files a Python
scan reads; scans use the same rules through the shared parallel walk
(`ingest::walk`, whose `python` list is tested to select exactly what `ingest_lang`
selects) and a stamp index, so unchanged files are not read again (see "Agent
hooks"). The TypeScript ingest is unchanged. Python ingest takes `.py`, and skips:

- `.pyi` stubs, as declarations (like `.d.ts`): the runtime never imports them;
- environments (`.venv`, `venv`, any directory holding `pyvenv.cfg` or a conda
  `conda-meta/`), `__pycache__`,
  `site-packages`, `.tox`, `.nox`, `.eggs`, `*.egg-info`, tool caches;
- generated code: `# Generated by ...` / `DO NOT EDIT` / `@generated` in the
  leading `#` comments, protobuf output (`*_pb2.py`, `*_pb2_grpc.py`);
- schema migrations: numbered Django migrations (`migrations/0001_initial.py`) and a
  `migrations/__init__.py`, Alembic and Flask-Migrate revisions (`alembic/versions/*`,
  `migrations/versions/*`). Django also writes a `# Generated by Django` header.
  Other modules under a `migrations/` directory (`django/db/migrations/autodetector.py`,
  an Alembic `env.py`) are code;
- files nested deeper than 1,000 levels (`too_deep`, every language): a byte scan
  before parsing bounds bracket depth and, for Python, the potential tree depth
  (brackets, indentation and the tokens of comma-free runs such as `x.a.a.a...`).
  String bodies are skipped, but the replacement fields of f- and t-strings (any
  prefix mix with `r`/`b`, triple-quoted ones over many lines, nested strings and
  format specs) and of template literals (`${...}`) are code and are scanned as such.
  Parsers, visitors and the recursive drop of a tree recurse per level, so a few
  hundred kilobytes of `(` would otherwise abort the process. CPython rejects more
  than 200 nested parentheses, and no file in the 24 eval repos is affected;
- the shared rules: `.gitignore`, `node_modules`, `dist`, `build`, files over 1 MiB,
  minified lines. (`build` and `dist` directories are skipped by name, which also
  hides a real package called `build`, as in pypa/build.)

## Lowering: Python to facts

| Python | Fact |
| --- | --- |
| `def`, `async def` at module level | `Symbol` kind `function`; `typed_return` when annotated |
| `class` | kind `class`; bases as `Wrap { kind: Extends }`, decorators as `Decorator`; kind facts in `traits` (below) |
| `X = ...`, `X: T = ...`, `type X = ...`, `a, b = ...` | `const` when `UPPER_CASE`, else `variable`; `function` for a lambda or a wrapped def (`h = login_required(view)` is a `Call` wrap) |
| Definitions inside top-level `if`/`try`/`with` | Module-level symbols (first definition wins); `if TYPE_CHECKING:` bodies are types and skipped, their `else` is not |
| Other top-level statements | The `(module)` pseudo-symbol, as in TypeScript |
| Decorators | `Wrap { kind: Decorator }`, outermost first, canonical (`pkg:flask_login#login_required`); `@method_decorator(x)` records `x` |
| Calls | Distinct canonical callees, plus first-call order |
| Keyword arguments | `args` entry `callee@99:keyword` (below) |
| `raise X(...)` / `raise X` | control `throw`, `throws` = canonical `X`; builtins are `global#ValueError` |
| `try` | control `try`; a body that is a single `try` is a `Try` wrap |
| `await` | control `await` |
| `typing.Any` in an annotation | control `uses_any` |
| pydantic `model_validate`, DRF `is_valid`, `jsonschema.validate` | control `validates` |
| `os.environ["X"]`, `os.environ.get("X")`, `os.getenv("X")` | `reads` = `os.environ.X` |
| `# drift-ignore D-abc123: reason` above a declaration | `suppressions` (a reason is required) |
| A class's own `class Meta:` (Django models, forms, filtersets, serializers, graphene types) | `meta`: `model=<canonical class>`, and `abstract` / `proxy` when set to `True`; an inherited `Meta` is not recorded |
| A class decorator called with a reference first (`@admin.register(Site)`, `@register_type(models.Site)`) | `decorator_args`: `decorator=argument`, both canonical |
| A docstring that explicitly negates a name (`Not a ChoiceSet`, `doesn't fit RepositoryBase`, `is not registered with register_filterset`) | `disclaims`: `Name=phrase`, the name as written (dotted stays dotted) and the phrase rebuilt from the negation, a fixed vocabulary (articles; whole-word forms of `use`/`extend`/`subclass`/`inherit`/`derive`/`fit`/`decorate`/`register`/`implement`/`build` and their prepositions; `subclass of`) and the identifier, within one clause. The clause must be about the symbol: no subject, or `it`, `this`, `this <noun>`, `the class` or its own name. Nothing is recorded for another subject (`Callers that do not use X`), a passive clause with an agent (`Not used by X`; `decorated by` / `registered by` are about the symbol), a question, `need not`, a docstring that says the exception is pending (`TODO`, `FIXME`, `yet`), capitalised words straight after a negation (`Not Found`), all-capital words (`NOT NULL`) and `None`/`True`/`False` |
| Parse errors | `parse_ok: false`; facts are best effort from ruff's recovered AST |

**Symbol kinds (`traits`, GAPS P1).** A class records what kind of class it is,
so mining can keep unlike classes apart (see [Mining on Python](#mining-on-python)):

| Trait | From |
| --- | --- |
| `enum` | a base `enum.Enum`/`IntEnum`/`StrEnum`/`Flag`/`IntFlag`, Django `TextChoices`/`IntegerChoices`, `graphene.Enum`; `@enum.unique`, `@strawberry.enum`; a subclass of an in-repo enum |
| `namedtuple`, `typeddict` | a `typing`/`typing_extensions` `NamedTuple` or `TypedDict` base, also through in-repo bases |
| `protocol` | a `typing.Protocol` base |
| `dataclass` | `@dataclass` (stdlib, pydantic), attrs `@define`/`@frozen`/`@attr.s` |
| `abstract` | an `ABC` base, `metaclass=ABCMeta`, an `@abstractmethod`, `class Meta: abstract = True` |
| `base` | named `*Mixin`, `Base*` or `Abstract*`; in a `base.py`, `base_*.py`, `bases.py` or `mixins.py` module; extended by two or more production classes (tests do not count); or named `*Base` and extended or abstract. A concrete parent extended once (a Django multi-table or proxy parent, a serializer refined once) and a `KnowledgeBase` stay primary |
| `view` | a class-based view whose handler methods are the entry points (`PostDetail.get`) |

The first three groups come from lowering and the linker; `base`, `view` and
inherited kinds from a repo pass (`crates/drift-py/src/kinds.rs`). TypeScript records
no traits yet, so its facts are unchanged; `Symbol.traits` is skipped when empty.
`LOWERING_VERSION` is 2.

**Keyword-argument encoding.** TypeScript records object-literal keys as
`callee@<arg index>:<key>`. Python passes options by keyword, which has no
position, so keywords are recorded at the reserved index 99:
`pkg:fastapi#HTTPException@99:status_code`. Mining parses the same shape, so a rule
reads "pass `status_code` to HTTPException()". Dict literals passed positionally
are data in Python, not options, and are not recorded.

**Scoping.** A name bound in a function (parameter, assignment, `for`, `with`,
`except`, walrus, `match` capture, local import) shadows the module binding;
`global` declarations do not; class bodies are not visible from their methods;
comprehension variables are scoped to the comprehension. Local imports resolve as
imports. Calls on parameters and `self.x()` are not recorded (TypeScript does the
same for parameters).

**Exports.** Python has no export statement. A module's exports are its static
`__all__` when it has one (including `+=`, `.extend`, `.append`); otherwise every
public (not `_`-prefixed) name it defines, plus explicit re-exports: `import x as x`
anywhere, and in a package `__init__.py` every name imported from the repo
(`from .core import Engine`, `from . import plugins`), following the typing spec's
re-export convention. `from x import *` is a `re_export_all`, expanded into the
names it brings. Entry-point symbols are always exported, so `_private_route`
handlers are still units.

## Resolution

Canonical module ids are repo-relative POSIX paths (`app/api/deps.py`,
`app/__init__.py`, a namespace package's directory `src/mylib/contrib`), stdlib
`pkg:python:<dotted module>` (`pkg:python:os.path`, like TypeScript's `pkg:node:fs`),
third-party `pkg:<dotted module>` (`pkg:fastapi.security`; named by module, not by
distribution, which a checkout cannot know), and `unresolved:<spec>`. These are the
ids of `Import` facts.

References are `<module>#<name>[.<member>]` at the name's origin. For third-party
and standard-library code they are folded at the top-level module:
`pkg:<top>#<rest.of.dotted.path>`. So `from rest_framework import viewsets;
viewsets.ModelViewSet` and `from rest_framework.viewsets import ModelViewSet` are
both `pkg:rest_framework#viewsets.ModelViewSet`, `os.path.join` is
`pkg:python:os#path.join` however `os.path` was imported, and the subpackage stays in
the name, so `pkg:django#db.models.Field` and `pkg:django#forms.Field` are distinct.

**Import roots** (where `import x` looks), derived from packaging metadata:

1. every project (directory with `pyproject.toml` or `setup.cfg`, or a `setup.py`
   that is not a module of a package, i.e. not next to an `__init__.py`)
   contributes its configured package directories (setuptools `package-dir` and
   `packages.find.where`, poetry `packages[].from`, hatch wheel `packages` and
   `sources`, the uv build backend's `module-root`, pdm `package-dir`, maturin
   `python-source`, setup.cfg `package_dir = =src` and `where`, setup.py
   `package_dir={"": ...}` and `find_packages("src")`), then a `src/` that is not
   itself a package, then the project directory; paths that leave the repo are ignored;
2. every directory holding `manage.py` (a Django project root);
3. the repository root.

uv, poetry or hatch workspace members are projects in their own right, so a
monorepo (langchain's `libs/*`) resolves across packages.

**File system.** Names are matched against cached directory listings by exact
case, as importlib's `FileFinder` does, so macOS's case-insensitive file system
resolves exactly like Linux (`import Models` next to `models.py` is not found).
Symlinks are not followed, as in ingest: a link out of the repo is never crawled.

**Order for one importing file**, following `sys.path` and importlib:

1. the file's base directory, the first ancestor without `__init__.py`
   (`sys.path[0]` for a script, pytest's "prepend" rule for tests);
2. the standard library;
3. the roots of the file's own project, then its Django root, then every other root.

Within that path, importlib's `FileFinder` order: a regular package (`x/__init__.py`)
beats a module (`x.py`) in the same entry; a directory without `__init__.py` is a
namespace portion, used only if no entry has a package or module. A namespace
directory counts only when it holds Python code within three levels: in a real
environment an installed distribution of the same name would win over an empty
directory, and a checkout has none to ask.

**Relative imports** climb from the file's directory; climbing past the deepest
import root that contains the file is "beyond top-level package" and unresolved.
(This is lenient for scripts: code that uses relative imports is meant to run as a
module.)

**Attributes versus submodules.** `from pkg import name` is the attribute when
`pkg/__init__.py` binds `name` (so `from .foo import foo` shadows the submodule, as
in CPython), otherwise the submodule. `import a.b.c` binds `a`, and `a.b.c.f()`
walks submodules to `a/b/c.py#f`. Origins follow every binding, not just exports:
`from app.models import User` in `app/crud.py` makes `app.crud.User` resolve to
`app/models.py#User`. Star imports are searched last, latest first.

## Entry-point adapters

Adapters describe how code runs; they never choose conventions. Decorator routes
are recorded as candidates at lowering and confirmed by the linker, because the
receiver is often imported (`from app.api import router`). A receiver is a router
when its class is a known router class, an in-repo subclass of one
(`class VersionedRouter(APIRouter)`), or, when the class comes out of a factory
(polar's `APIRouter = get_api_router_class(...)`), carries a router class's name.
A decorator whose receiver is not a router stays a plain decorator wrap.

Entry points have the TypeScript shape (`symbol`, `kind`, `method`, `route`,
`adapter`); routes are joined with every mount prefix (`/?` marks a prefix that is
not a literal, such as `prefix=settings.API_V1_STR`).

| Framework | Recognised | Guards (wraps) |
| --- | --- | --- |
| FastAPI | `@app/router.get/post/put/patch/delete/options/head/trace/api_route/websocket`, `add_api_route`; `APIRouter(prefix=)`, `include_router(prefix=)` chains across files | `Depends`/`Security` in parameters (default or `Annotated[T, Depends(f)]`, including aliases such as `CurrentUser` defined in another file), `dependencies=[...]` on the route, the router, `include_router` and `FastAPI()`; sub-dependencies follow, depth first |
| Flask | `@bp.route/get/post/...`, `add_url_rule`; `Blueprint(url_prefix=)`, `register_blueprint(url_prefix=)` (overrides, as in Flask), nested blueprints, app factories (blueprints imported inside `create_app()` included) | `@bp.before_request` / `bp.before_request(f)` hooks of the blueprint and its parents; app hooks (kind `app_hook`, shown as `X (app hook)`): hooks on an app or the factory's local app (`app.before_request(f)`, a nested `@app.before_request`, or in a helper the app is passed to, `init_hooks(app)`, for every factory that passes it) and `@bp.before_app_request`, a hook of every app the blueprint is registered on; decorators such as `@login_required` |
| flask-restx / flask-restful | `@ns.route("/x")` on `Resource` classes, `Api(blueprint)`, `add_namespace(ns, path)`, `add_resource` | class and method decorators |
| Django | `urlpatterns` with `path`, `re_path`, `url`; `include("app.urls")`, `include(local_list)`, `include(module)`; `+=`, `.append`, `+ router.urls`; only what `ROOT_URLCONF` reaches (below); `admin.site.urls` as one `django_admin` entry on `urlpatterns` | wrappers at registration (`login_required(views.x)`), decorators, mixins (`Extends`), `@method_decorator`; `AdminSite.admin_view` (active staff users) on the admin entry; `LoginRequiredMiddleware` from settings (not on DRF views) |
| DRF | `router.register("users", ViewSet)` mounted by `include(router.urls)`; `APIView`/`ViewSet` subclasses, also through in-repo bases; `@api_view` | `permission_classes` (class attribute or decorator) as `Call` wraps, also inherited from an in-repo base, otherwise the settings' `DEFAULT_PERMISSION_CLASSES`; `AllowAny` is an `opens` wrap, not a guard; `authentication_classes` and `DEFAULT_AUTHENTICATION_CLASSES` are `authenticates` / `config_authenticates` wraps, not guards |
| Celery, Dramatiq | `@shared_task`, `@app.task` on a `Celery` app, `@periodic_task`, `@dramatiq.actor`: kind `job`, route = task name (Celery's default is `module.function`, the module's import name from the deepest import root holding it; Dramatiq's is the function name); beat schedules (`beat_schedule`, `CELERY_BEAT_SCHEDULE`, `CELERYBEAT_SCHEDULE`, `app.conf.update(beat_schedule=)`, `add_periodic_task(..., task.s())`) and `@periodic_task` add a `cron` entry on the task, route = the schedule entry's name; also a function decorated with an in-repo wrapper that calls `dramatiq.actor` or `shared_task` (polar's `@actor(...)`), route = the function name | — |

**Class-based views.** A view class (DRF, Django `View`, Flask `MethodView`,
flask-restx `Resource`, or an in-repo base ending in `View`, `ViewSet` or
`Resource`) gets one symbol per handler, `PostDetail.get` or `UserViewSet.list`
(DRF actions and `@action` methods included), carrying the class's wraps plus its
own decorators. Registrations attach entry points to the handlers, so per-method
guards (CTFd's `@admins_only` on `Resource.get`) are visible. Views without handler
methods (a bare `ModelViewSet`) are one entry with method `ANY`.

**How dependencies become conventions.** FastAPI dependencies are recorded as
`Call` wraps, the slot TypeScript uses for middleware, so mining proposes "HTTP
handlers in ... are wrapped in get_current_user()" (read: depend on). A
dependency on a configured instance (`_read = Authenticator(scopes=...)`) is
recorded as its class, the same identity `Depends(Authenticator(...))` written
inline has and the same rule TypeScript applies to `withAuth(opts)`; a class's
`__init__` dependencies join the chain for `Depends(Class)`, its `__call__`
dependencies for an instance. Mining's "one of these wrappers" rule picks its
alternatives from the outermost call wrap, which for FastAPI is the first
dependency in parameter order, so repos whose handlers list several dependencies
get long variant sets (polar's first proposal lists 16 alternatives, 228 of 370
being `Authenticator`). Holders are counted by that outermost dependency too, after
chains are resolved (below), so census still lists a route whose outermost dependency
is none of the alternatives; `check` counts any call wrap.

**Dependency chains (F12).** A route meets "depend on X" when it reaches X through
another dependency, up to 8 levels: a dependency function whose own parameters depend
on X (`get_current_active_user` on `get_current_user`, `Security(...)` too), an
`Annotated[..., Depends(X)]` alias (also one built on a `Depends(X)` constant,
`ApiKeyDep = Annotated[str, API_KEY_REQUIRED]`, or on another alias), `dependencies=[...]`
on the route, its router, `include_router` or `FastAPI()`, and a class dependency's
`__init__` (for `Depends(Class)`) or `__call__` (for an instance). In a variant set
("wrapped in A or B") the chain does not make a holder: a member counts by its
outermost dependency, so a login start whose only path to a set's non-auth member
(`get_db_session`) is a chain stays an outlier in census, the evidence read before
accepting. A route whose outermost dependency is an alias of a `Depends(f)` constant
(`ApiKeyDep`) counts as `f`.

A chain never lets a weaker dependency count as a stricter one:

- a dependency made soft is no dependency of its class or factory:
  `Depends(HTTPBearer(auto_error=False))`, `Depends(get_auth(required=False))` and
  `optional=True` add nothing, and a module-level instance built so
  (`optional_scheme = OAuth2PasswordBearer(..., auto_error=False)`) stands for itself,
  not for `OAuth2PasswordBearer`. A value of `auto_error`, `required` or `optional`
  that is a name, a call or another non-literal expression (`auto_error=not DEBUG`)
  counts as soft, and so does a `**kwargs` argument; a string, number, `None` or a
  list, tuple, set or dict display (`Roles(required=["admin"])`) does not.
  Positional arguments are matched to the callee's positional parameters
  (positional-only included; keyword-only ones are never bound, and `*args` takes
  the rest): an in-repo function, an in-repo class's own `__init__` or, without one,
  its first base's (`SubAuth(False)` with `class SubAuth(Auth)`), and
  `OAuth2PasswordBearer`/`OAuth2AuthorizationCodeBearer`. When what they bind is
  unknown, positional arguments count as soft: a `*args` argument, a decorated
  class without `__init__` (a dataclass), a class whose first base is a package's;
- a chain does not follow a dependency whose name's qualifier says it is soft: a
  leading `optional`, `maybe`, `anonymous`/`anon`, `soft`, `lenient`, `public`,
  `guest`, `unauthenticated` or `nullable` (after `get_`, in `snake_case` or
  `CamelCase`) on who is asking (`user`, `session`, `principal`, `account`, `auth`,
  `token`, ..., optionally after `current`, `active` or `authenticated`: `public_user`,
  `get_optional_current_user`, `MaybeAuth`), or a trailing `_optional`, `_or_none`,
  `_or_anonymous`, `_or_anon`, `_or_guest`. `Depends(get_optional_user)` counts as
  `get_optional_user` only, even when it depends on `get_current_user`;
  `verify_public_key`, `public_key_auth` and `optional_scopes_user` are followed;
- a dependency's parameter that may be `None` (`user: User | None = Depends(f)`,
  `Optional[...]`, `Annotated[str | None, Depends(f)] = None`, an alias whose type is
  optional) does not join the chain of its dependents. On the route itself it still
  counts: the route names it.

A name with "auth" in it proves nothing: what counts is what the dependency depends on.
The fixture `crates/drift-py/tests/fixtures/fastapi-deps` has each shape and each soft
case; `python_dependency_chains_hold_in_census_check_and_hooks` (hooks.rs) checks the
census counter-case, that `check`, PostToolUse, Stop and MCP agree on a constant alias
and a soft dependency, and that single-file facts equal the full scan's. The Python
fact cache is rebuilt once (`LOWERING_VERSION` 9); the facts schema is unchanged.

**Settings and global guards.** Django settings are read from the module a literal
`DJANGO_SETTINGS_MODULE` names in `manage.py`, `wsgi.py` or `asgi.py`
(`os.environ.setdefault(...)` or `os.environ[...] = ...`), or, when there is none,
from every `settings.py` and `settings/*.py`. They are bound as Python binds them:
star imports (`from .base import *`) first, later ones rebinding earlier ones, then
the module's own statements in order. A plain assignment (`MIDDLEWARE = [...]`,
`REST_FRAMEWORK = {...}`) rebinds the setting, and a `REST_FRAMEWORK` key it leaves
out is DRF's default; `+=`, `.append`, `.insert`, `[*MIDDLEWARE, ...]`,
`REST_FRAMEWORK["KEY"] = ...`, `.update` and `{**REST_FRAMEWORK, ...}` extend it.
Only literal values count (also in `if`/`try` blocks).

- *URL roots.* With settings found, these URLconfs and what they include (URLconfs,
  DRF routers) serve requests: `ROOT_URLCONF`, every other string setting ending in
  `URLCONF` (django-tenants' `PUBLIC_SCHEMA_URLCONF`), the `host()` URLconfs of a
  `*HOSTCONF` module (django-hosts), and literal `request.urlconf = "..."`
  assignments in the project. A URLconf included from several places takes its
  prefix from a reached parent.
- *Pruning.* A URLconf in the project directory (the directory `ROOT_URLCONF`'s dotted
  name is relative to) that no root reaches serves nothing and has no entry points,
  but only when the roots are known to be complete: every root was found, and no
  reached URLconf has an include Drift cannot follow (`include(get_urls())`, an
  f-string, an imported pattern list). A directory with its own `manage.py`,
  `wsgi.py` or `asgi.py` naming other settings (or none) is a separate project.
  Everything else keeps the fallback, as when no settings are found: each URLconf is
  a root. Hiding an entry point is worse than listing one too many. (On netbox,
  `include(get_model_urls(...))` makes the roots incomplete, so nothing is pruned.)
- *Global guards* are wraps of kind `config`, outermost, with the class's canonical
  id: `LoginRequiredMiddleware` (or an in-repo subclass) in `MIDDLEWARE` on every
  plain Django view and the admin, except views with `@login_not_required` (on the
  view, its class's `dispatch`, a base class, or `login_not_required(view)` in the
  URLconf) and Django's own `LoginView` and password-reset views. Not on DRF views:
  DRF 3.16 sets `login_required = False` on every `APIView`, viewset and `@api_view`
  (older DRF on Django 5.1 is guarded; Drift does not read installed versions and
  under-reports here). DRF's `DEFAULT_PERMISSION_CLASSES` apply to every DRF view that
  declares (or inherits from an in-repo base) no `permission_classes`. When several
  settings modules serve a URLconf, a guard applies only if all of them set it.
- *Not guards.* Authentication identifies the caller and rejects nothing: per-view
  `authentication_classes` are `authenticates` wraps, `DEFAULT_AUTHENTICATION_CLASSES`
  `config_authenticates` wraps, listed by `drift security` under `authenticates`
  (`TokenAuthentication (settings)`). `AllowAny` and `@login_not_required` are `opens`
  wraps, listed under `opens`. So `permission_classes = []`, `AllowAny`, or an unset
  `DEFAULT_PERMISSION_CLASSES` (DRF's default is `AllowAny`) is unguarded unless a
  plain Django view is under the middleware. Schema decorators (drf-spectacular's
  `extend_schema`, drf-yasg's `swagger_auto_schema`) are not guards either.
- `drift security` lists settings guards with their source, `TokenPermissions
  (settings)`, and app-wide Flask hooks as `csrf (app hook)`, with a count of entry
  points guarded only by app hooks. Mining ignores `config`, `config_authenticates`
  and `app_hook` wraps, so it never proposes "views are wrapped in X" for what one
  setting or one app-level registration does.

On netbox (`DEFAULT_PERMISSION_CLASSES = TokenPermissions`) unguarded HTTP entry
points fall from 210 to 74; the rest are Django class-based views whose guard is a
mixin (`ConditionalLoginRequiredMixin`, an `Extends` wrap, which `drift security`
does not count) and open DRF views (`TokenProvisionView`, `permission_classes = []`).
On CTFd, every route runs the app's `before_request` hooks; 21 (`/login`, `/setup`, ...)
have nothing else.

**"Unguarded" for FastAPI.** `drift security` counts an entry point as unguarded
when it has no wrapper at all. Every FastAPI dependency is a wrapper, so a route
whose only dependency is a database session (`Depends(get_db)`) counts as guarded:
for FastAPI, "unguarded" means "no dependency at all", which can hide
unauthenticated routes that use a session. Read the guards column.

**Models.** Django models (`models.XField`, `ForeignKey`), SQLAlchemy
(`__tablename__`, `Column`, `mapped_column`, `Mapped[...]`) and SQLModel
(`table=True`) become `Model` facts with `source` `django`, `sqlalchemy` or `sqlmodel`.

## Agent hooks

The hooks and MCP tools work on Python files as they do on TypeScript. Every Python
convention is a suggestion (D7), and agents are shown a suggestion only when its rule
family is admitted for Python (at least 85% accepted of at least 10 labelled cards on
the latest dev run, `crates/drift-mine/data/family-admission.json`) or a person shows it
with `drift review --show-to-agents <id>` (README, "What agents are shown"). On the
current table (dev relabel 4) no Python family is admitted, so the hooks and MCP tools
show agents Python conventions only when a person chose them.

**Before a new file is written** (PreToolUse `Write`, MCP `drift_rules_for` with
`content`), `drift_py::preview_file` lowers the planned content in memory, on a
64 MB stack, after ingest's content gates (size, generated name or header,
minified lines, the drift-core nesting guard; `.pyi` stubs too). Only roles that
match what it declares are primed: classes or functions, HTTP handlers, jobs,
models. To recognise a router, a Celery app or a view base class defined elsewhere,
the preview reads the in-repo modules the content looks up (following re-exports, at
most 64 files in 6 rounds); a DRF viewset or Django/Flask view class that nothing
registers yet gets the entry points a registration would give it, so a new viewset
file is primed with the rules for HTTP handlers. Files that mount routers elsewhere
are not read, so prefixes and inherited guards are absent, and only the file's own
project roots are import roots. Content a scan would skip gets no rules (it will not
be checked); content that does not parse gets the rules grouped by what they apply
to ("if it exports HTTP handlers: ..."), because it will still be checked but what it
declares is unknown.

**Model conventions.** `roles::role_covers_path` matches a Django, SQLAlchemy or
SQLModel model role to a file that declares models of that ORM when its models are
known (an existing file, or planned content), and otherwise to where models live: a
`models.py` or a module directly in a `models/` package (`models/user.py`, not
`models/llama/layers.py`, which is more likely ML code). `check` and PostToolUse already
reported model violations by the model's file; the change makes priming,
`drift example` and `drift_rules_for` see them.

**Package facts.** Every directory holding Python code (or an ancestor of it) with a
`pyproject.toml`, or with `requirements*.txt` and no `pyproject.toml`, is a
`PackageFacts` (`crates/drift-py/src/packages.rs`). Dependencies (`name@range`,
names normalised as in PEP 503, environment markers dropped, `*` when unpinned) come
from PEP 621 `[project] dependencies` and `optional-dependencies`, PEP 735
`[dependency-groups]`, Poetry `dependencies`, `dev-dependencies` and
`group.*.dependencies`, and uv's legacy `dev-dependencies`; `requirements*.txt` are
read when there is no `pyproject.toml` or it declares its dependencies `dynamic`. A
uv workspace root without `[project]` declares its dependency groups; its members are
packages of their own. Scripts are task-runner tasks (poe, pdm, taskipy, hatch's
default environment), the counterpart of npm scripts; console entry points are like
`bin` and are not recorded. The new optional `manifest` field names the file the facts
came from, so package units and their violations use `pyproject.toml` or
`requirements.txt`; it is omitted for `package.json`, so TypeScript output is
unchanged. Python packages form their own role (`file: pyproject.toml`, "Python
packages"), apart from npm's: an npm convention (a `clean` script) is never checked
against a `pyproject.toml` or primed into a new one, Python packages never count
toward npm evidence, the root of each ecosystem's workspace is skipped by that
ecosystem's own count, and dependency-version majorities are computed per ecosystem.
Python dependencies are not used for framework mandates, which name npm packages.
Package rules (`PackageHas`, `DependencyVersion`) are in the suggestion tier for both
ecosystems, so Python package conventions advise and are marked `(suggestion)`; one
blocks only after `drift review --block <id> --force`. A directory with both a `package.json` and a
`pyproject.toml` declares what either declares. With these, layering's "declared
dependency" exception and the package role (dependency versions, scripts) work for
Python: on langchain, `libs/core` declares `langchain-text-splitters`, so the
proposal "files in libs/core/\*\* do not import from libs/text-splitters/\*\*" (2
outliers that import it) is no longer made, and "workspace packages use the pytest
version most workspace packages use" (21/22) is (now worded "Python packages use ...").

**After an edit** (PostToolUse), a `.py` file is checked from a single-file scan
(`drift_py::scan_file`) instead of a full scan. A stamp index
(`.drift/cache/index-py-*`) records each file's stamp, hash, content skip reason and
whether its content reaches *other* files' facts: it mounts routers or includes
URLconfs, registers views, adds hooks, passes a factory's app to a helper, sets
`request.urlconf`, schedules Celery beat entries, or is a Django entry script
(`manage.py`, `wsgi.py`, `asgi.py`) or settings file (`settings.py`, `settings/*.py`).
Those files are always linked with the edited one: they decide URL roots and which
URLconfs serve nothing, settings guards (login middleware, DRF defaults), app-wide
hooks and `cron` entries. Settings modules named by an entry script and the modules
they star-import are found by lookup. When the edited file defines Celery tasks and the repo
has beat schedules, every file that may define a task is linked too, because a beat
names its task by Celery name. The edited file is linked against those files plus the
modules the link looks up: the linker runs in a tracking mode that records every
in-repo module it asked for and did not have (a file, or a file's routers,
dependency aliases, dependency functions or instances), those are added, and the
link repeats until nothing is missing. Every table entry comes from the file it
names, so at that fixed point every lookup gets the answer a full link gets. Test
pairing, the file's models, Python packages and the TypeScript packages and linter
configs (from the same walk) complete the facts. A package manifest edit, or no
index yet, runs a full scan as before.

### Oracle method

`eval/oracle-py/oracle.py` re-resolves every import Drift reports
(`drift debug py-imports`) with `importlib.machinery.PathFinder.find_spec`, CPython's
own finder, over an emulated `sys.path`. No repository code runs. The `sys.path` is
re-implemented in Python from the same policy (`tomllib`, `configparser`, setup.py
patterns, `manage.py`): separate code, same rules. Relative imports go through
`importlib.util.resolve_name`.

For every `from X import name` row the oracle follows `name` to its origin with its
own reading of CPython's `ast`: module-level bindings in statement order, then
submodules, then star imports, then a module-level `__getattr__`. Drift must report
the same defining file and name, the same submodule, or an external or unresolved
origin when the oracle reaches one. A name that is neither bound in `X` nor a
submodule is a **gap** (CPython raises `ImportError`). The oracle also parses a
sample of 400 files per repo with CPython's `ast` and compares module-level names
with Drift's symbols, expected exports with Drift's exports, and parse success.

The gate fails on any `DISAGREE*` or `GAP*` row, including an import Drift leaves
unresolved that Python finds outside the repo, or the reverse.

What it checks: Drift implements its documented root policy and CPython's finder
order (package over module, namespace portions, base directory before the standard
library, relative-import bounds, submodule walks, attribute shadowing, re-export
chains), and its parser sees the same module-level names as CPython. What it does
not check: the root policy itself (where roots come from, the stdlib's position, the
namespace-with-code rule, cross-project fallback), which both sides share; whether a
project is really run with these roots; compiled extensions and `.pth` files; and
`from X import name` when `X` is installed code (`name_external`, 29,914 rows) or
resolved only at runtime (`name_unjudged_dynamic`, 22 rows: module `__getattr__`,
external star imports). A check against a resolver Drift did not write (pyright or
ty, or `importlib.util.find_spec` in a real `uv sync` environment) is a follow-up.

The re-export check found one policy bug that the earlier oracle could not see,
because both sides had it: a module named `setup.py` inside a package (polar's
`organization_review/collectors/setup.py`) made its directory a project root, so
the package's relative imports were "beyond top-level" on both sides. Both are
fixed: a `setup.py` next to an `__init__.py` is a module, not a project.

**Single-file checks.** A rule that follows base chains reads the base classes: the
TypeScript single-file scan (`drift_ts::scan_file`, used by the hooks) follows the
in-repo `extends` targets of the file's classes, at any depth, and returns their class
symbols as `RepoFacts.context_files` (context for rules, not checked themselves), so a
hook reports what `drift check` reports for `ZEmail extends MidEmail extends Mailer`.
The Python single-file scan does the same, and runs `kinds::classify` over the file,
its base-class files and the files of its in-repo decorators, so inherited kinds, view
classes and jobs declared through a wrapper come out as in a full scan. Whether a
class is a `base` counts the classes that extend it across the repo, so when any
other production file names one of the file's classes as a base (a name the scan
index records per file), the single-file scan returns `None` and the hook runs a full
scan. So does either language when a base chain is longer than 64 files. PostToolUse
and Stop therefore put a file's classes in the same roles (`hooks.rs`
`python_post_tool_use_and_stop_agree_on_class_roles`), and `drift debug incremental`
compares each sampled file's roles as well as its facts. Whether a top-level
`integration/` directory is an integration-test suite (`roles::NonProduction`) counts
all of its test files, in both languages, so a single-file scan of a file below an
`integration` directory, in either language, carries the path and package of the other
analysed files below one as `RepoFacts.integration_files` (the other language's vouched for by its
scan index). A hook therefore leaves a Nest fixture app (`integration/*/src`) out of
every role, as `drift check` does (`hooks.rs` `single_file_scans_see_integration_suites`).

**Policy compatibility.** Conventions accepted before this change keep their ids, and
an accepted `avoids: any` on Python code keeps meaning `typing.Any`. But the members of
some roles change on upgrade: a class that becomes a `base`, `abstract` or `view` (or
an enum, dataclass, ...) leaves the role of primary classes, so a rule about it stops
applying to it; and a function decorated with an in-repo job wrapper (polar's
`@actor`) moves from the functions role of its file to the job entry points role, so
an accepted rule on that functions role no longer covers it, and a rule on the job
role starts to. Code that was not a member before can therefore break an accepted rule
without being in `drift.lock`: re-run `drift init` (or re-baseline the lock) after
upgrading.

- a standard-library name and its backport (`typing_extensions`/`typing`, `tomli`/`tomllib`,

  facts, `mine::BACKPORTS`);

  a production Python class or function named `N` that stands in for a library
  reference whose last name is `N`. A class stands in for the library classes named `N`
  it extends, directly or through in-repo bases (`CTFd/forms/fields.py#SubmitField

  `Decimal(graphene.Float)` calls `decimal.Decimal` but is no decimal). A function

  argument, `*args` or `**kwargs`, and to every library call of that name (the
  `forwards` trait: polar's `button(**kwargs)` calling `tag.button(**kwargs)`), not one
  it only calls (a `load()` that opens one
  settings file and calls `json.load(fp)`). It must also be a shared helper: no entry
  point or script (a recorded route, job or cron, a view class, a management command,
  `__main__.py`, `manage.py`, or a file under `scripts/`, `bin/` or a hidden directory;
  not a whole `views/` package, where Misago keeps its admin `render`), and production
  code in at least three other files references it. A library reference two such
  helpers claim has no team version. Review of #35 found same-name callers that are not
  versions of what they call: a Django view `login` calling `auth.login`, polar's
  backoffice handler `get` calling `pycountry.countries.get`, polar's worker `run`
  calling `asyncio.run`, saleor's scalar `Decimal`.

The population is the role's members that use the thing, directly or through an in-repo
base (`PlanState(AgentState)`, `AgentState(TypedDict)`), outside the module that
defines the team's version, which uses the library by design. The source most of them use
is the rule; members that also reference another source are its outliers. A team version
must be that source: "use the library, not the team's version of it" is never mined,
since a same-name helper does not make the team's code the outlier. (langchain_core's
`dumps` and `loads` are referenced from fewer than three other production files; uses
from the monorepo's other packages resolve to `pkg:langchain_core`, so the three-file
bound drops them.) `evidence.split` counts each member once, as
the rule judges it (holders under the source, an outlier under the first alternative it
uses), so it adds up to the evidence. Like `before`, the rule is counted over the users
only: `role.members` is the number of users, and census emits no `exempt` list for it;
`check` gives the other members of the role an exemption reason. There is no
lift test (the choice is between sources of one thing), so the bound is the usual
`MIN_LOWER_BOUND` over at least `MIN_ROLE_SIZE` users, and Python holders must come from
three files. Over the same holders, `imports_from` is kept before a `calls` rule
(priority 1): where the outliers take the thing from says more than that the holders
call it. Python only, so the TypeScript census does not change. `check` treats the
role's other members as holding it ([`Rule::exemption`]: "does not use `TypedDict`", and
"its module defines a `button` the rule names" for the team's own module). A team version
reads "use the team's `button` (server/polar/backoffice/components/_button.py), not
`tagflow.tag.button`": the file that defines it, since members import it from various
re-exports, and the library reference spelt as code.

- `forwards` (new, recorded at lowering, `LOWERING_VERSION` 7): a function that passes
  one of its own parameters to every library call of its own name, as
  `def load(fp, **kw): return json.load(fp, **kw)` does. A parameter counts as passed
  when it is the call's first positional argument, `*args` or `**kwargs` (not an
  optional keyword: `requests.get(API + path, timeout=timeout)` is not about
  `timeout`), and the function has not reassigned it before the call
  (`fp = open("settings.json")`) nor a nested function rebound it. In-repo callees
  (itself when it recurses, a module-level `session.get`) and built-ins are left out;
  one same-name library call that gets none of its parameters (`os.environ.get` next to
  a forwarded `session.get`, `asyncio.run` next to `subprocess.run`) means no trait. It
  is what makes a function a team version (above). Recall limits: a parameter inside an
  expression (`json.loads(s.strip())`), a lambda and `functools.partial` do not
  forward, and a walrus does not count as reassigning.

  class goes to a full scan.

## Known gaps

- Django: views registered by custom decorators (netbox's `register_model_view`) are
  not entry points. There is no generic rule to follow: the decorator stores the view
  in a registry, and a different function (`get_model_urls`) turns the registry into
  `path()`s at import time.
- Django: settings are literals only. `DJANGO_SETTINGS_MODULE` is read from
  `os.environ.setdefault` in `manage.py`, `wsgi.py` and `asgi.py`, not from the
  environment, `--settings`, pytest's `DJANGO_SETTINGS_MODULE` or
  django-configurations; settings brought in by `from .base import NAME` (rather than
  `*`) or computed (`MIDDLEWARE = base.MIDDLEWARE + [...]` with an attribute) are not
  followed. Statements inside `if DEBUG:` count as always run.
- Django: mixins (`LoginRequiredMixin`, netbox's `ConditionalLoginRequiredMixin`) are
  `Extends` wraps, which `drift security` does not count as guards (TypeScript base
  classes share that rule), so class-based views guarded only by a mixin read as
  unguarded. The admin is
  one entry point; `ModelAdmin` permissions are not modelled.
- DRF: `get_permissions()` / `get_authenticators()` overrides are not read (the
  defaults are assumed), nor are `permission_classes` set by third-party base classes.
  Decorators other than schema ones count as guards, whatever they do.
- Flask: a helper's parameter is matched to the factory's app only when the app is
  passed directly (`init_hooks(app)`, positionally or by keyword); hooks registered
  through `app.before_request_funcs` or extensions (`init_app`) of installed packages
  are not seen. Hooks are listed in name order, not registration order.
- FastAPI: ASGI middleware is not a guard; prefixes that are not literals render as `?`.
- Jobs: a Celery task's default name uses the deepest import root holding its module,
  which can differ from how the worker imports it; beat entries naming tasks Drift
  does not find, schedules assigned from a variable, and `django-celery-beat`
  database schedules are not `cron` entries; a job declared through an in-repo
  wrapper of `dramatiq.actor` (polar's `actor`) is named after the function, not its
  `actor_name=`.
- Dynamic imports (`importlib.import_module`, `__import__`) are not imports.
- Resolution: compiled extensions and `.pyi`-only modules are not targets; a
  namespace package's id is its first portion; setuptools `package-dir` entries for
  single packages (other than `""`) are not read.
- Package facts: `setup.py` and `setup.cfg` dependencies (`install_requires`) are not
  read, `requirements/` directories (`requirements/base.txt`) and `-r` includes are
  not followed, and a project with only `setup.py`/`setup.cfg` and no requirements file
  is no package. Python linter configs (ruff, flake8) are not read.
- Model files outside `models.py` and `models/*.py` are matched to model conventions only
  when their models are known (existing files, planned content), not by path.
- Previews of new files: route prefixes and guards inherited from mounts in other
  files are absent, imports of sibling projects stay `pkg:` ids, and at most 64
  modules are read; views registered by custom decorators are not recognised.
- Mining's variant slot is the first call wrap (see FastAPI above): which alternatives
  a variant set lists, and which members hold it, depends on parameter order. Ordering
  parameter dependencies by canonical id after router and mount dependencies would
  make it independent of parameter order; deferred.
- Dependency chains (F12): soft dependencies are recognised by keyword or positional
  flag, name qualifier and optional parameter type, not by reading their bodies; a soft
  dependency under another name and signature is followed like a strict one, and a
  positional flag of a package callee other than the two OAuth2 bearers is not read.
  An instance of a class without its own `__call__` does not follow its base's
  `__call__` dependencies (under-counting only).
  `census` (variant sets by outermost dependency) and `check` (any call wrap) still
  disagree on a route that reaches an alternative only through a chain or a later
  parameter: census flags it, `check` passes it. `add_api_route(..., dependencies=[...])`
  guards are not followed into their chains. A dependency returned by a factory
  (`Depends(get_user(scopes=...))`) counts as the factory, whose own parameters are
  not followed.
- A router mounted under several parents (`include_router(r, prefix="/v1")` and
  `prefix="/v2"`, a blueprint registered twice) gets the routes and inherited
  dependencies of one parent only (the first reached from `ROOT_URLCONF` for Django,
  else the lexicographically first).
- Symlinked directories inside the repo are not import targets (Python would follow
  them).
- Long chains in TypeScript that nest without brackets (`a + a + ...` over hundreds
  of thousands of terms) are not bounded; the TypeScript scan bounds brackets only.
- `__all__` built dynamically falls back to public names.
