# Does Drift work? Precision study and agent A/B (2026-11-05)

> **Dated record (2026-11-05).** This page records Drift as it was on that date and is
> kept as written, apart from this note. It is not current documentation:
> behaviour, output and figures may have changed since. The [README](../../README.md)
> describes the current product, and its
> [Limits of the beta](../../README.md#limits-of-the-beta) gives the current
> precision figures and their sources in `eval/study/runs/`. Precision figures
> here are development-set figures under the tier and rubric of their date, and
> none is a held-out result. Under decision D7 the default tier is TypeScript
> call wrappers and layering only, Python advises only, and the default tier
> ships as advise until it measures ≥ 95% on a held-out set.

Two questions decide whether Drift is a product:

1. **Are its proposals conventions a maintainer would accept?**
2. **Does it change what coding agents do?**

Both were measured on the 16 pinned repos in `eval/repos.json`.

## 1. Precision of proposals

### Method

- Drift's default `census` (top 15 per repo) produced 183 proposals.
- Four independent reviewers (Claude subagents) labelled them, one group of
  repos each, following the rubric in [`eval/study/RUBRIC.md`](../../eval/study/RUBRIC.md).
  The reviewers saw neither Drift's code nor any expected result.
  - **ACCEPT:** a maintainer would plausibly enforce it on new code.
  - **TRIVIAL:** true, but the framework or language already enforces it.
  - **WRONG:** it misdescribes the code, groups unlike things, or its outliers
    are legitimately different.
- Each reviewer opened the example and at least two outliers before deciding.
- A fifth reviewer independently relabelled a random sample of 40, without
  seeing the first labels.
- All labels, with one-line reasons, are in
  [`eval/study/labels.jsonl`](../../eval/study/labels.jsonl).

### Agreement

| | |
| --- | --- |
| Exact agreement (3 labels) | 73% |
| Cohen's κ | 0.51 (moderate) |
| ACCEPT vs not | 75% |
| WRONG by the second reviewer that the first also called WRONG | 8 / 8 |

The labels are noisy at the TRIVIAL/ACCEPT boundary, but reliable on WRONG.

### Results, before and after fixing what the labels exposed

| | Proposals | ACCEPT | TRIVIAL | WRONG |
| --- | --- | --- | --- | --- |
| Before | 183 | 96 (52%) | 28 (15%) | 59 (32%) |
| After  | 181 | 108 (60%) | 30 (17%) | 43 (24%) |

New proposals that appeared after the fixes were labelled by two further blind
reviewers, using the same rubric.

### By rule kind, after

| Rule | n | Accepted |
| --- | --- | --- |
| Call wrappers (`withWorkspace()`, `authActionClient...`) | 22 | 91% |
| Base classes | 11 | 82% |
| Argument keys (`permission` passed to `Authenticated()`) | 16 | 69% |
| Layering (internal import avoidance) | 13 | 62% (was 17%) |
| Decorators | 22 | 59% |
| Rendered components | 13 | 54% |
| Calls | 27 | 44% |
| Naming | 24 | 42% |
| Other avoidance (`any`, bare `Error`, `console`) | 13 | 31% |

**The core thesis holds where it matters most.** Guards and wrappers, base
classes and required arguments are accepted at 69–91%. The weak kinds are
generic calls, naming and absence rules.

### What the labels exposed, and the fixes

| Problem | Evidence | Fix |
| --- | --- | --- |
| Import avoidance flagged legitimate use of shared packages (`@novu/shared`, a logger, `provider-utils`) | 20 of 24 internal-import rules WRONG | only propose when the target area itself imports the role's area (a dependency cycle) |
| Avoiding packages (`react`, `next`) restated what a layer is | 2 of 11 accepted | not proposed |
| Imports inside one package counted as layering (trpc `www`) | 2 WRONG | same-package imports ignored |
| `"use client"` proposed as a convention | 0 of 3 accepted | directives are never proposed |
| Class symbols inherited every method's decorators (immich "controllers are decorated with `Authenticated`", which is applied per method) | 3 WRONG in immich | classes keep class decorators only |
| `Controller` from `@nestjs/common/decorators` differed from `@nestjs/common` | novu outliers that were not outliers | package refs compared by package root |
| A component body `=> (<BaseEmailWrapper>...)` was not seen as a layout wrapper | infisical false outlier | concise arrow bodies count |
| `onRequest: (req, res, done) => { verifyAuth(...)(req, res, ...) }` was not seen as a guard | infisical false outliers | guards read from inline hook bodies, including curried guards and continuations |
| `drift review --block` let small roles block | found while setting up the A/B | flags respect the 15-member minimum, like interactive review |

**Caveat:** the fixes were checked on the same 16 repos they were derived from.
"After" is optimistic; a held-out set of repos is the next precision check.

### Outliers that were real bugs

Reviewers were asked only to judge conventions, but several noted outliers that
look like defects in the projects themselves:

- **infisical, a confirmed defect.** `backend/src/server/routes/v2/deprecated-project-router.ts`,
  `GET /:workspaceId/encrypted-key`, attaches `verifyAuth` to `onResponse`
  instead of `onRequest`. Authentication runs after the handler has returned the
  encrypted project key. Severity is probably limited: a global identity hook and
  service-level permission checks still apply, but the route's auth-mode
  restriction is not enforced. It was surfaced as an outlier of "v2 routes are
  wrapped in `verifyAuth()`".
- **dub, a hardening issue.** `banPartner` and `forceWithdrawal` are raw helpers
  exported from `"use server"` files next to their wrapped `*Action` versions.
  Next.js treats such exports as server actions. They are only called from
  server routes today.

## 2. Agent A/B

### Method

- Nine tasks in three repos (dub/Next.js, immich/NestJS, infisical/Fastify +
  React), listed in [`eval/agent-ab/tasks.json`](../../eval/agent-ab/tasks.json).
- Each task is worded the way a developer would ask, with no mention of
  conventions.
- Each task ran in a fresh worktree with headless Claude Code (`claude -p`),
  same prompt, tools and turn limit, in two arms:
  - **control:** the repo as is;
  - **drift:** `drift init`, every proposal accepted (block where the role has
    15+ members), and the plugin's hooks and skill installed exactly as users
    would install them.
- Scoring: new violations, in the files the agent changed, of conventions the
  independent reviewers labelled ACCEPT.
  - Drift therefore does not grade itself on rules no maintainer would want.
  - Added `drift-ignore` suppressions are counted, as a check for gaming.
- Runner and scorer: [`eval/agent-ab/`](../../eval/agent-ab/).

### Results

| Model | Arm | Runs | Violations of accepted rules | Suppressions added | Turns | Cost | Time |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Opus 5.5 | control | 9 | 0 | 0 | 127 | $3.61 | 501 s |
| Opus 5.5 | drift | 9 | 0 | 0 | 127 | $3.60 | 504 s |
| Haiku 5.5 | control | 9 | 0 | 0 | 111 | $0.13 | 312 s |
| Haiku 5.5 | drift | 9 | 0 | 0 | 140 | $0.15 | 419 s |

**On these tasks, Drift made no difference to the final code.** Without Drift,
both models found and copied the neighbouring code:
- `withWorkspace` and `withPartnerProfile` on new dub routes;
- `authActionClient` on the new server action;
- `@Authenticated({ permission })`, `@Endpoint`, `BaseService` and
  `*Repository` in immich.

### What happened inside the Drift runs

Final-state scoring hides two events visible in the hook state:

- **A real catch (immich, Haiku).** The agent's first edit inserted the new
  route between an existing `@Authenticated(...)` decorator and its handler.
  That silently removed authentication from `GET /albums/:id/map-markers`.
  - The PostToolUse hook reported the new violation on that handler.
  - The agent's summary: *"Drift warning appeared because my first insert put
    the new route between an existing `@Authenticated` decorator and its
    handler. I moved the decorator and the warning cleared."*
  - This is the failure Drift is for, and it was prevented.
- **A cost of a wrong rule (infisical, Haiku).** "Backend files do not import
  react" (labelled WRONG: email templates must) advised and blocked once, and
  the agent spent extra turns complying.
  - A team reviewing proposals would have rejected it.
  - In the A/B every proposal was accepted, which overstates the cost.

### What this means

- **The pain is not where the pilot looked.** Single, well-scoped tasks in
  areas full of examples are the easy case: agents copy neighbours.
- **The catch shows where the value is.** Drift helps when an edit breaks
  something away from the line being written: a decorator stack, a sibling
  handler, a layering boundary. Agents don't re-check what they didn't mean to
  touch, and the final diff can still look fine to a reviewer.
- **Wrong rules have a real cost.** The review step (`drift review`) is part of
  the product, not a formality, and precision has to keep rising.

### Not tested yet

- Long sessions, multi-file features and work after context compaction.
- Tasks that create a new area with no neighbours.
- Vague prompts ("quick fix", "just make it work").
- Repeated runs: one run per cell, so any rate here has a wide interval.
- Drift as a pre-merge check on human and agent PRs, rather than only in-session.
