## Targets (what "95%" means)

- **Not-wrong rate ≥ 95%:** (ACCEPT + TRIVIAL) / all proposals shown, on a
  held-out set of repos never used for tuning. This is what agents and CI feel
  as false alarms. Today, on the dev set only (the repos the fixes were tuned
  on, so optimistic; the held-out number is not measured yet):
  - **TypeScript, 16 repos:** 83.5% not-wrong, 73.2% accepted, of the 164
    proposals shown once #13's new proposals were labelled
    ([P1 progress](#p1-progress-symbol-kinds), PR #13). Measured on #13 merged
    with main, which had #16's 12 unlabelled proposals: 84.2% not-wrong and
    74.3% accepted (113) over the 152 labelled proposals
    ([PYTHON.md, Mining on Python](PYTHON.md#mining-on-python), PR #13). Round 2
    (#18) leaves the TypeScript census byte-identical
    ([PYTHON.md, Round 2](PYTHON.md#round-2-relabel-of-13)).
  - **Python, 8 repos:** 83.3% not-wrong (and accepted) over the 24 labelled
    proposals, 57.1% with the 11 unlabelled of the 35 shown counted as wrong
    (round 2 merged with main, the
    [Round 2 effect table](PYTHON.md#round-2-relabel-of-13), PR #18).
  - When this plan was written: 76% for TypeScript (138 of 181, ACCEPT +
    TRIVIAL after the first fixes, [STUDY-2026-11-05.md](STUDY-2026-11-05.md)).
- **Default-tier accept rate ≥ 95%:** ACCEPT / proposals in the default
  (blocking-eligible) tier, on the held-out set. Weaker rule kinds are shown as
  suggestions, not defaults. The product now computes this tier (see
  [Tiering](#tiering)); the held-out number is still to be measured.
- **Yield is reported with precision:** accepted conventions per repo, and
  recall against conventions the repo documents itself (lint rules, AGENTS.md,
  CONTRIBUTING). Precision without yield is not a result.

## Tiering

Every proposal and every convention has a confidence tier, computed from its
structured rule kind and its role's size by `drift_mine::tier::tier_of`. It is
the definition pre-registered for the primary held-out sets
([`eval/study/README.md`](../../eval/study/README.md) rule 5, the manifests'
`tier`), not a new one:

- **default** (blocking-eligible): `wrapped_by:call`, `wrapped_by:decorator`,
  `wrapped_by:extends`, `passes_key`, `avoids:import`, `renders`,
  `wrapped_by:jsx`, and the role has ≥ 15 members;
- **suggestion:** everything else, including kinds added later (the default
  tier is an allowlist) and default kinds in smaller roles.

`eval/study/tier-cases.json` is run through the Rust function
(`tier::tests`) and through `lib.mjs`'s `tierOf` (`eval/study/tier.test.mjs`,
in CI), and the Rust test also checks its kinds and threshold against both
primary manifests, so the product and the study cannot disagree. On the 24 dev
repos, the 215 proposals of this branch's census get the same tier from both.

The tier is never written to `conventions.yaml`: ids, files and a person's
`status`/`mode` are unchanged, and a later change of definition re-tiers
without rewriting a policy.

**What blocks and what advises (the beta claim).** Only conventions in block
mode block (the Stop hook, `drift check` exit 1), and `drift init` proposes
everything in advise mode. `drift review` sets default-tier conventions to
block on `b`/`--block`; a suggestion needs an explicit confirmation (typing
`block`) or `--block <id> --force`, and roles under 15 members never block. So
what blocks is default-tier conventions a person chose to block, plus any
suggestion a person forced. `drift check` treats `mode: block` in a role under 15
members as advise, even in a hand-edited policy. Suggestions already in block mode
(policies written before tiering, or `--force`) keep blocking. The agent A/B
(`eval/agent-ab`) now builds its policies the same way: ACCEPT-labelled
default-tier conventions block, suggestions advise, never `--force`. Agents see default-tier rules first when priming a
new file (at most 2 suggestions of 4 rules) and suggestions labelled as such in
advice; `drift_rules_for` gives each rule's tier, and the AGENTS.md export
groups rules and suggestions. `census` lists the default tier first, ranked as
mined within each tier; which proposals are shown is unchanged (census ids on the
16 TypeScript and 8 Python dev repos are identical before and after, only the
order and the tier labels change).

`eval/study/runs/dev-py-2026-11-05/final.jsonl` (Python); unlabelled counted as

**Update 2026-11-06: decision D7 narrows the tier.** Approved by the founder and
recorded before any held-out census ([study decision log](../../eval/study/README.md#decisions-before-any-held-out-census-2026-11-05),
`eval/study/tier-d7.json`). The default tier is now TypeScript/JavaScript call
wrappers (`wrapped_by` with wrap kind `call`) and layering (`avoids:import`)
only, with D5's conditions on top (every target in the repository: no `pkg:`,
`global#` or `unresolved:`; a role of at least 15 members). Decorators, base
classes, JSX layout wrappers and every other kind are suggestions. **Python has
no default tier:** every Python convention is a suggestion (`tier_reason:
language_advise`). The release gate is unchanged: a language's default tier
ships as advise until it measures ≥ 95% default-tier accept under rubric v3,
judged per D1, on a primary held-out run. Under D7, on the v3 dev relabel
(`eval/study/runs/dev-v3-2026-11-06/*/views/d7`, dev figures, not held-out),
the TypeScript default tier accepts 24 of 32 (75.0%; call wrappers 14/19,
layering 10/13), against 35 of 52 (67.3%) under D5; the Python parts have no
default tier (D5 had 3/10 and 6/14 there). The per-violation analysis behind D7
projects TypeScript call wrappers and layering to about 96% on dev once the
planned round-5 fixes land, while Python class rules stall at about 55–64%.

## P1 progress: symbol kinds

**Python: done for classes; TypeScript: not yet.** Driven by the Python dev study
(`eval/study/runs/dev-py-2026-11-05`, 7 mixed-group WRONG labels); details and numbers
in [PYTHON.md](PYTHON.md#mining-on-python).

- **Facts.** `Symbol.traits` (language-neutral, skipped when empty): `enum`,
  `namedtuple`, `typeddict`, `dataclass`, `protocol`, `abstract`, `base` (named or
  placed like a base or mixin, extended by several production classes, or `*Base`
  and extended or abstract; a concrete parent extended once stays primary) and
  `view` (a class represented by its handler methods). `drift-py` fills them
  (`crates/drift-py/src/kinds.rs`); `drift-ts` does not, so TypeScript facts are
  byte-identical.
- **Roles.** `roles::class_variety`: base, abstract and view classes are in no role;
  the special kinds form roles of their own (`RoleSelector.variety`, serialised only
  when set, so no existing id changes). The rule is language-neutral: TypeScript
  adopts it by filling `traits` (abstract classes, classes other classes extend,
  `enum`-like objects, pass-through re-exports).
- **Shared fixes that came with it** (TypeScript too): a class extends what its
  in-repo bases extend, for holders and for `check`, but an ancestor is a candidate
  only when most holders extend it directly; a layering rule needs a role apart from
  the target area and the dominant direction of the cycle (or a declared package
  edge). On the 16 TypeScript dev repos: 3 labelled WRONG layering rules and 1
  accepted `renderEmail()` rule (now "extend BaseEmail", same holders) gone, 1
  accepted layering rule back, 2 new and 3 accepted rules with fewer outliers;
  labelled accept 72.0% to 73.2%, not-wrong 82.3% to 83.5% after labelling.
- **Hooks.** Both single-file scans carry the in-repo base classes of the file as
  `RepoFacts.context_files`, so a hook checks a chained subclass as `drift check`
  does; the Python one also runs `kinds::classify` over the file, its bases and its
  decorators' files, and falls back to a full scan when another file may extend one
  of its classes (`base` counts subclasses) or a chain is longer than 64 files.
- **Round 2 (Python):** file kinds split by layer (`api/views`, `graphql/filters`),
  unrouted views by ancestry, type variables in no role, numbered modules no kind,
  layering against an area's peers, refinements of a team base; see
  [PYTHON.md](PYTHON.md#round-2-relabel-of-13).
- **Round 3 (Python, relabel r2):** the round adds these rules:
  - rules that restate a role's variety are not proposed;
  - what a rule is about (`Rule::exemption`): value-typed enum bases; classes named for a base of another kind under base-class rules, only when the target's whole ancestry is known (fail-closed); keys only for callers of the callee;
  - optional keys per call (`Symbol.omits`);
  - no call order for class bodies;
  - classes inherit the attributes their bases declare and they do not rebind (`Symbol.declares`, per attribute).

  See [PYTHON.md](PYTHON.md#round-3-relabel-r2). The helper rule is language-neutral:
  one TypeScript proposal loses an outlier, and no id moves.
- **Still open for P1:** co-located helpers and pass-through re-exports in
  TypeScript, generated-file markers, and helper classes next to Python models
  (polar's `orm.mapped_column()` rule still holds exceptions and schemas).

## Classes of another kind and the target's module (F3, F4)

From the rubric v3 error analysis of the D5 default tier on the dev set (dev repos
only; no held-out repo, manifest or result read), revised after the review of #45. Its
class K ("another kind of class") and D ("the target's own module") outliers are
exempted per outlier, with a reason, through `Rule::exemption` (#27). Exemptions are
shown wherever Drift reports: `census --json` (`exempt`) and the text census
(`exempt:` lines on the card the labellers see), `drift check` (`exempt` in
`--format json`; a count and the first ten in text), and the hooks (PostToolUse names
the ones the edit adds, Stop the ones the turn added, once, without blocking). A hook's
single-file scan defers to a full scan when it cannot decide. No id, rank or tier
moves; no proposal appears or disappears.

**One invariant for every exemption: none under a guard rule, none for an entry point**
(`Rule::exemption_allowed`, asked first by every exemption path: value-typed enums,
classes named for their own base, classes of another kind, the target's module, keys
to a callee never called). A guard rule's target wraps, decorates or is a base of an
entry point (for a route that is a method, its class counts: a Nest controller's base),
or its name says access control (`security::names_access_control`: `requires_auth`,
`TenantScopedModel`, `RowLevelSecurityModel`). An entry point is the member itself, a
class one of whose methods is a route, or a class a route's handler runs directly: it
constructs it or calls a method on it (`app.post("/x", (req, res) => new
XHandler().handle(req, res))`, a Flask view's `return XHandler().handle(request)`, a
static `X.verify()`, a method passed as the handler). When the handler runs the class
(constructs it, or passes it or its method as the handler), what it is built on guards
the route too, so "extend `BaseHandler`" is a guard rule when routes run its
subclasses; a static call (netbox's `DeviceFaceChoices.values()` in a view) does not
make `ChoiceSet` a guard (follow-up to #45, `RepoContext::is_entry_class`,
`class_run_by`). Classes a handler calls (`class_run_by`) and classes a route refers to
by reference (`ref_target`, below) fill one set of entry classes, which
`RepoContext::is_entry_unit` and so every exemption path read. Only the target's own
class passes the guard condition (it is the guard, not a member it guards).

**The gate's blind spots, closed (`ws/gate-harden`).**

- *Handlers routed by reference.* `router.get("/x", handler)` makes the route a symbol
  of the routes file that calls `handler(ref)`; the handler had no entry point of its
  own. Now a unit an entry point refers to by reference is an entry point
  (`RepoContext::is_entry_unit`), and a class is an entry class when a route refers to
  its method (`Controller.list`) or to a method of an instance its module builds
  (`ctrl.list` with `const ctrl = new Controller()`). What such a handler is wrapped in
  or built on guards it (`RepoContext::is_guard`): a `BaseController` not named for
  access control is a guard once routed controllers extend it. `drift-ts`
  (`LOWERING_VERSION` 23, after #38's 22) records the reference inside a wrapped or bound handler too
  (`asyncHandler(ctrl.list)`, `ctrl.list.bind(ctrl)`, nested), flattens handler arrays
  (`router.get("/p", [auth, h])`: `auth` is middleware, `h` the handler), and records
  what an object literal's properties refer to (`export default { list }`,
  `const ctrl = { create }`) as `(ref)` calls of the object: a route on `ctrl.create`
  makes the object and every function its properties refer to entry units. A hook's
  single-file scan does not load the routes file, so there such a handler is not an
  entry unit; an exemption that would follow only from that is undecided and defers to
  a full scan (`crates/drift-cli/tests/by_reference.rs`). A route body that constructs
  a controller (`(req, res) => new Controller().list(req, res)`) is left to #68, and an
  instance built by a DI container (`container.resolve(C)`) is not followed.
- *Guards called in the body.* A rule "calls `f()`" is a guard rule when
  `security::callee_is_guard` says so: nothing in `f`'s name opens access, and its name
  says access control; or its definition throws an error named for rejecting the caller
  (`ForbiddenError`, `UnauthorizedError`), itself or one call deep; or entry points
  (handlers by reference included) call it directly in two units or more
  (`context::ENTRY_CALLERS`) and its body can throw (`ensureOwnsProject`). A class
  called as a constructor is never one. No exemption applies to such a rule today; the
  gate refuses any later one.
- *One word list.* `security::ACCESS_CONTROL_WORDS` is the only access-control word
  list (the F7/F8 guard check reads it too; since ws/auth-vocab it is
  `vocab::refuse::WORDS`, beside the grant vocabulary `vocab::grant`). It gains `authorize`, `authorise`,
  `authenticate`, CASL's `can` (a whole word only: not `cancel`, `scan`, `candidate`),
  `ability`, `protect`, `permit`, `signed`, `verify`, `credential`, `apikey`,
  `ratelimit`, `throttle`, `ownership`, `owns`, `member` (so `listMembers` too),
  `membership`, `entitled`, `entitlement`, `allowed`, and the phrases `require` + `user`
  (`requireUserId`) and `user_passes_test`. `user` alone is not in it.
- *`…OrThrow` is no opening.* `security::auth_class` reads `or` as weakening
  (`withAuthOrNull`) except before a word that turns the caller away (`throw`, `raise`,
  `fail`, `redirect`, `401`, `403`, `404`, …): `getUserOrThrow`, `assertMemberOrThrow`
  and `get_user_or_404` are not public.
